# DocumentWorkflowAPI — 민감 데이터 판별 및 문서 형상관리

RD-SRS **5.x의 민감 데이터 판별(DLP)**과 **9.x의 문서 형상관리**를 구현하는 서버 프로젝트입니다.
문서 저장·수정 시 버전을 생성하고, 민감정보 검사, 변경 이력·비교, 상태·승인, 알림 및 보존 정책을 제공합니다.

현재 실행 구현은 `docversion/`의 **Java 21 · Spring Boot · MyBatis · MariaDB** 기반 멀티모듈입니다.
Nextcloud의 버전·활동·워크플로 구조를 참조했으며, 제공하는 Docker Compose는 **Nextcloud와 연동하지 않는 독립 실행 구성**입니다.

> 기본 기능의 시연과 개발 검증이 가능한 단계입니다. 전체 요구사항의 운영 검증이 완료된 상태는 아니며,
> 검사 누락·부분 검사 판정·보존 정책 등 보완 항목이 있습니다. 5.5는 의도적으로 확장 인터페이스와 골격만 유지합니다.

## 요구사항과 구현 범위

### RD-SRS-5.x — 민감 데이터 판별

| 항목 | 요구사항 | 현재 구현 및 담당 범위 |
|---|---|---|
| 5.1 | 저장 문서의 민감 데이터 자동 구분 | 신규 버전마다 전체 검사(FULL)를 예약하고 결과·탐지 항목을 저장·조회 |
| 5.2 | 수정 자료의 민감 데이터 실시간 구분 | 수정 버전의 FULL 검사와 diff 추가 줄 기반 DELTA 검사. 현재 비동기 후처리이며 실시간 지연 기준 검증 필요 |
| 5.3 | 승인 없는 외부 반출 차단 | 리얼시큐 Client 담당. USB·인쇄·이메일·클라우드 반출 차단은 이 서버 단독으로 제공하지 않음 |
| 5.4 | 다양한 민감정보 형식 식별 | 주민번호·신용카드·계좌·휴대전화·이메일 규칙, 체크섬·문맥 검증, 점수 산정 및 탐지값 마스킹 |
| 5.5 | 머신러닝 기반 고급 탐지 | **이번 구현 범위에서 보류.** 휴리스틱의 한계로 인터페이스·골격만 유지하며 현재 판정에 참여하지 않음 |
| 5.6 | 민감정보 유형·분류 기준 관리 | 리얼시큐 Web 담당. 서버는 DB 규칙 적재·요약 조회·reload 제공. 규칙 변경 API는 미제공 |
| 5.7 | 문서 반출 요청 및 승인 | 리얼시큐 Web 담당. 9.7의 문서 내용 승인과 별도 기능 |

FULL은 해당 버전 전체의 판정을 위한 검사이고, DELTA는 이번 수정에서 추가된 줄을 검사하는 보조 수단입니다.
결과는 `SENSITIVE`, `NOT_SENSITIVE`, `UNDETERMINED`로 구분합니다. 작업 상태인 `PENDING`, `PROCESSING`, `FAILED`도 함께 확인해야 합니다.
`NOT_SENSITIVE`는 규칙 점수의 합이 임계값보다 낮다는 의미이므로 민감정보 패턴이 전혀 없다는 뜻과 같지 않습니다.

### RD-SRS-9.x — 문서 형상관리

| 항목 | 현재 구현 |
|---|---|
| 9.1 | UUID 버전 식별자와 문서별 증가 리비전 번호 |
| 9.2 | 수정본 업로드 시 자동 버전 생성, 문서 행 잠금으로 리비전 경합 제어 |
| 9.3 | 변경자·시각·사유·대상 버전 기록, 변경 내용은 diff로 별도 조회 |
| 9.4 | 인접 버전의 비동기 diff, 지원 문서의 텍스트 추출 및 해시 비교 폴백 |
| 9.5 | 특정 시점 기준 버전 목록과 버전 콘텐츠 다운로드 |
| 9.6 | 초안·검토중·승인·수정본 초안·폐기 상태 및 전이 이력 |
| 9.7 | 승인 요청·승인·반려·취소·번복, 전원·과반·순차 결재 및 위임 |
| 9.9 | 이해관계자 인앱·이메일 알림, 아웃박스와 재시도 |
| 9.10 | 보관 기간·최대 버전 수 정책, 범위 지정 및 자동 정리 |

9.8은 명세서에 없습니다. 위 표는 구현된 기능의 범위이며, 아래 제약을 포함한 전체 인수 시험 통과를 의미하지 않습니다.
클라이언트나 외부 저장소에서 발생하는 변경은 이 서버의 업로드·수정 API로 전달되어야 합니다.

## 저장소 구성

```text
DocumentWorkflowAPI/
├── README.md
├── DocumentVersionWorkflowAPI.cpp   # 9.x 선행 C++ 의사코드
├── Diffservice.h                    # 선행 diff 설계
├── Schema.sql                       # C++ 단계 스키마
├── Review_notes.md                  # 의사코드 검토 이력
├── docversion/
│   ├── pom.xml                      # Maven 부모 프로젝트
│   ├── dlp-core/                    # 5.x 탐지 엔진과 API, Spring 비의존
│   ├── docversion-app/              # 9.x 서비스, HTTP API, DB 및 DLP 연계
│   ├── dlp-eval/                    # DLP 평가 문서·정답표·측정 스크립트
│   ├── compose.yaml                # 앱·MariaDB·Adminer·MailHog
│   ├── Dockerfile
│   └── INSTALL.md
├── MoM/                            # 회의 자료
└── report/                         # 보고서
```

C++ 자료는 9.x 업무 규칙의 선행 설계 기준입니다. 해당 업무 규칙을 변경할 때는 C++ 설계와의 정합성도 확인합니다.
실행 방법·DB 마이그레이션·현재 DLP 동작은 Java 구현을 기준으로 설명합니다.
앱이 사용하는 스키마는 `docversion-app/src/main/resources/db/migration/`의 Flyway **V1~V18**입니다.

## 실행

Docker Engine과 Compose가 필요합니다. 앱은 컨테이너에서 빌드하므로 실행만 할 때 호스트에 Java·Maven을 설치할 필요는 없습니다.

저장소 루트에서:

```bash
cd docversion
docker compose up --build
```

| 서비스 | 주소 | 용도 |
|---|---|---|
| 앱 | http://localhost:8080 | API와 시연 콘솔 |
| Adminer | http://localhost:8081 | DB 조회 |
| MailHog | http://localhost:8025 | 시연용 이메일 수신함 |

기본 `demo` 프로필에서는 사용자 테이블이 비어 있을 때 `alice/alice123`, `bob/bob123`, `admin/admin123` 계정을 생성합니다.
`admin`은 보존 정책·DLP 규칙·알림 아웃박스 관리 권한을 가집니다.
운영 환경에서는 `SPRING_PROFILES_ACTIVE=prod`를 지정하고 별도로 계정·접속 구성을 준비해야 합니다.

## 검증과 DLP 평가

Java 21과 Maven을 사용하여 `docversion/`에서 실행합니다.

```bash
mvn -pl dlp-core test   # 탐지 엔진 단위 시험, Docker 불필요
mvn test               # 전체 시험, MariaDB Testcontainers를 위한 Docker 필요
```

서버 기동 후 HTTP 통합 시험과 DLP 평가를 실행할 수 있습니다.

```powershell
powershell -ExecutionPolicy Bypass -File .\docversion_test.ps1
cd dlp-eval
powershell -ExecutionPolicy Bypass -File .\measure-dlp.ps1
```

2026-09-05 코드 검토에서는 기존 Docker 비의존 테스트 **74건(엔진 47건, 앱 27건)**이 통과했습니다.
해당 검토에서는 MariaDB·HTTP 전체 통합 시험, SMTP 전달 및 부하 시험을 재실행하지 않았습니다.

DLP 평가 자료에는 2026-08-31 측정 결과와 이를 반영한 V18 계좌·카드 규칙 조정이 기록되어 있습니다.
현재 평가 세트는 **문서 25종·파일 63개(TXT 25, DOCX 19, PDF 19)**입니다.
기존 측정 기록, 수정 후 회귀 시험, 최신 전체 평가 결과는 구분해서 해석해야 합니다.

## 알려진 제약과 보완 항목

- **DLP 판정:** 앞 500만 자까지만 검사하고도 비민감을 확정할 수 있습니다. 부분 추출·부분 검사를 전체 검사와 구분하도록 보완해야 합니다.
- **작업 내구성:** 버전 커밋 이후 DLP·diff 작업 적재가 실패하면 자동 복구되지 않을 수 있습니다. 기존 버전의 검사 작업 백필도 필요합니다.
- **실시간성:** FULL 검사는 기본 15초 주기로 최대 20건씩 순차 처리합니다. 수정 수신부터 판정 완료까지의 지연 상한은 검증되지 않았습니다.
- **보존 정책:** 폴더 `/a`가 `/abc`까지 포함하는 접두 검색, 중첩 정책의 최소 보관 기간 충돌, 정책 수정값 검증 누락이 남아 있습니다.
- **비교·시점 조회:** 비연속 버전 비교 작업을 요청 시 생성하지 않으며, 시점 이전 결과가 없으면 미래 버전을 반환하는 경로가 있습니다.
- **승인·검사 정합성:** 승인 대리인의 열람 권한, DLP 결과 저장의 트랜잭션, 실행 중 재검사 경합을 보완해야 합니다.
- **형식·크기:** HWP 추출은 미지원이며, 기본 업로드 상한은 20MB입니다. 파일 전송은 전량 메모리 적재 방식으로 100MB 동시 접근 평가를 위한 추가 작업이 필요합니다.
